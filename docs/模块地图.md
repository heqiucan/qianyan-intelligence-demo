# 模块地图

本文件说明依赖方向和跨模块交接，不记录每个按钮的细节。具体功能定位见 `docs/功能责任矩阵.md`。

## 系统分层

```text
用户界面
  frontend/src/App.tsx
    -> frontend/src/app/ 应用外壳、路由、主题、全局数据
    -> frontend/src/features/ 业务页面和局部状态
    -> frontend/src/api.ts 请求、错误、幂等、下载

HTTP API
  backend/main.py:create_app
    -> 领域路由注册
    -> backend/core/storage.py
    -> backend/model_adapter.py
    -> SQLite / 文件上传 / 本机 FFmpeg / Windows SAPI
```

## 前端依赖方向

```text
App.tsx  ----->  app/ (AppShell / pages / hooks)
  |                    |
  +------------>  features/*
  |                    |
  |                    +--> components/ui.tsx
  |                    +--> features/*/types.ts
  |                    +--> api.ts
  v
components / domain / visuals / shared CSS
```

### 页面层

- `App.tsx` 负责路由级组合、跨域交接和公共状态连接。
- `frontend/src/app/AppShell.tsx` 负责固定导航、顶栏、移动端菜单和内容框架。
- `frontend/src/app/pages.ts` 定义一级导航和面包屑，旧路径转换在 `frontend/src/navigation.ts`。
- `frontend/src/app/useWorkspaceNavigation.ts` 负责全局离开保护、历史、滚动和场次保留判断；业务模块仍有自己的编辑保护，不能假定全由此 hook 管理。
- `frontend/src/app/useWorkspaceData.ts` 负责活动和统计范围；Agent、知识、需求等组件还独立获取其业务数据。

### 业务层

- `agent` 负责 Agent 任务生命周期，不直接拥有知识事实或创意审批。
- `demand` 负责需求素材、筛选、结果和选题交接。
- `knowledge` 负责资料、检索、引用和草稿来源。
- `creative` 负责创意生成、编辑、事实核对、版本和审批。
- `ads` 负责计划、调整、模拟批次和启动确认。
- `analytics` 负责数据转换和可视化，不负责生成或保存报告。
- `feedback` 负责待办、复盘、观察和报告。
- `live` 负责直播场次、预览、互动、音频、话术和本地媒体资源。

### 允许的跨模块交接

```text
knowledge -> agent：资料空间、引用和草稿来源
agent -> creative：人工确认后的内容草稿
product -> creative：商品事实和商品版本
product -> live：商品目录、SKU 和货盘快照
live -> agent：场次、SKU、货盘版本上下文
creative -> ads：已确认素材快照
ads -> analytics：计划、批次、订单和消耗
analytics -> feedback：分析快照、复盘建议和报告
feedback -> creative/ads：人工确认后的新创意或计划调整草稿
```

跨模块传递应使用已有的 `handoff`、快照、版本字段或明确路由参数，不直接修改对方组件内部状态。

## 后端依赖方向

```text
backend/main.py
  create_app / Store.initialize / 公共输入和兼容导出
       |
       +--> backend/core/storage.py
       +--> backend/v2.py
       +--> backend/agents/
       +--> backend/knowledge*.py
       +--> backend/demand_*.py
       +--> backend/live*.py
       +--> backend/speech/
       +--> backend/media_tools.py
       +--> backend/model_adapter.py
```

### 后端规则

上图是应用装配方向，不表示已经消除反向依赖。`backend/v2.py`、`backend/live.py`、语音及互动模块仍从 `backend/main.py` 导入输入模型、幂等和公共函数；部分模块在 register 函数内部导入以配合启动顺序。后续抽基础层时需要检查这些导入，不能只移动文件。

- `backend/core/` 只能提供基础设施，不反向导入业务初始化和 `main`；这是后续变更约束，当前 storage 已满足。
- `backend/main.py` 当前仍是应用装配和种子/迁移入口；不因目录整齐一次性重写。
- 领域模块通过 `register_*` 方式注册路由，业务逻辑和领域测试保持在同一边界附近。
- 模型适配器负责回放、配置型号白名单、调用记录和错误边界；业务模块不直接拼接外部模型 HTTP 请求。历史“免费”核对日期不是永久定价承诺，真实调用前按当次授权和官方信息核实。
- 直播媒体处理和语音处理可以调用本机工具，但不能因此宣称已接入平台推流或实时音频设备。

## GEO 原型交接

```text
GEO 工作台（frontend/src/features/geo/）
  -> model.ts：本地样例、指标口径、项目/任务/草稿状态
  -> GeoWorkspace.tsx：路由视图、localStorage、本地模拟任务推进
  -> GeoOverview.tsx：总览与样例可见性图表
  -> GeoViews.tsx：品牌知识、问题监测、诊断任务、内容、报告
  -> GeoForms.tsx：项目/资料/问题表单、证据详情、内容审核弹窗

当前不调用 backend、不调用模型、不连接外部 AI 平台。
后续接入顺序：授权信源采集 -> 证据/版本存储 -> 外部回答采样 -> Agent 编排 -> 报告归因。
```

## 当前结构风险

- `App.tsx` 仍是前端跨域组合中心；新增业务应优先在 `features/` 内闭合，再把最小 Props 接到 App。
- `backend/v2.py` 仍聚合活动、创意、计划、分析、待办和报告；如果拆分必须先补领域 API/事务边界。
- `backend/live*.py` 和 `frontend/src/features/live/` 已按功能分文件，但尚未形成完整的后端 `live/` 子目录。
- 全局 CSS 仍有历史样式和新版主题覆盖层；新样式优先放模块 CSS，公共变量放主题文件。
- Codex 看板属于未提交的另一项任务，不能当作业务工作台依赖加入本模块地图。

## 影响检查实例

| 请求 | 起点 | 必须追踪的契约 | 验证范围 |
| --- | --- | --- | --- |
| 改商品价格 | PRODUCT | 商品版本→活动/货盘快照→旧创意确认→运行队列/计划→订单和报告历史 | 商品版本、创意、货盘及报价拦截；不得批量覆盖旧快照 |
| 改 Agent 完成条件 | AGENT | 草稿确认版本、引用有效性、任务 completed、转入创意的条件 | AGENT、HANDOFF、KNOWLEDGE；不必先全文读媒体工具 |
| 改顶栏/主题 | SHELL / THEME | 官网链接、移动导航、表单实例、音视频对象、打印隔离 | 主题/导航专项和涉及的状态保持 |
| 改定时报时 | INTERACTION | 已确认规则版本、运行场次、定时租约、语音许可、隐藏页暂停 | timer / interaction / speech相关用例 |

页面归属不等于数据归属：Agent入口中的需求任务仍用 demand_runs；知识草稿转入创意不让 Agent 直接拥有投放权限。记录依赖时注明是调用、数据来源、事件通知还是UI跳转，避免把所有连线误当成直接代码 import。
