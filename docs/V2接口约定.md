# V2 实施接口约定

实现阶段内部协作契约。旧记录兼容；不重置用户数据库。金额由后端计算。以下路径均带 `/api` 前缀。

## 基础扩展

- `GET /state` 保留现有字段，增加 `adjustments, batches, tasks, observations, reports` 数组。insights 必须返回。数组记录含 id/campaign_id/created_at，新增字段兼容旧记录。
- Campaign 增加 `audience,selling_point,goal,budget_limit,start_date,end_date,strategy_version,strategy_history`；默认字符串空、预算可空。POST /campaigns 接这些字段和 request_id；PUT /campaigns/{id} 编辑策略保存版本，输入同表单（request_id 可选）。goal 是内部观察目标文本，广告平台目标仍为商品成交。
- Product 增加 `evidence`（资料来源文本）。
- POST /campaigns/{id}/generate 原调用兼容，可带 `tone`（自然/简洁）、`angle`（场景/规格）用于预设回放。
- POST /creatives/{id}/regenerate `{tone,angle,request_id}` -> 单一新 Creative，属于原版本系列；不改另一组。
- Creative 增加 `family_id,template`（classic/minimal）、tone/angle；revise 可包含 template，旧行为兼容。
- OrderInput 增加 quantity 整数1..20，默认1；订单存 unit_price,quantity,plan_config_version，amount 后端用快照单价计算。

## 计划

- Plan 增加 config_version（默认1）,config_history 数组。
- PUT /plans/{id} `{name,budget,start_date,end_date}` 仅草稿可编辑，留版本。
- POST /plans/{id}/copy `{request_id}` -> 新 Plan 草稿，绝不复制订单/数据。
- POST /plans/{id}/adjustments `{budget,start_date,end_date,reason,request_id,insight_id?}` -> Adjustment。
- Adjustment: id,campaign_id,plan_id,before:{budget,start_date,end_date,config_version},after:{budget,start_date,end_date},reason,status(draft/applied),created_at,applied_at?,insight_id?。
- POST /adjustments/{id}/apply `{request_id}` -> Adjustment；版本冲突409，结束计划禁止；生成观察任务。调整不自动启动暂停计划。
- POST /plans/batch-status `{plan_ids,status:'paused',request_id}` -> `{results:[{plan_id,ok,error?}]}`，仅运行计划暂停，逐项反馈。
- 现有 status API 启动/恢复时校验当前日期属于计划周期。无自动日期调度。

## 筛选和模拟场景

- GET /analytics?dataset=history|session|batch&campaign_id=...&plan_id=...&batch_id=...&date_from=YYYY-MM-DD&date_to=YYYY-MM-DD。
- Analytics 保留现有字段，增加 orders（当前范围订单）,spend_entries（明细）,views,filters。rows 有 plan_id；新客按范围内购买时刻身份判断。session 可日期筛选；history 固定窗口，batch 固定批次，不支持日期筛选（传日期拒绝422）。不混合三个来源。
- GET /scenarios -> `[{id,label,description,impressions,clicks,spend,orders,new_customers}]`；固定场景 no_conversion / near_budget / followup_orders / followup_no_change。
- POST /batches/preview `{plan_id,scenario}` -> `{label,metrics,orders,spend_entries,window,note}` 只预览不存。
- POST /batches `{plan_id,scenario,request_id}` -> Batch；只接受 running 计划；批次有 id,campaign_id,plan_id,scenario,label,created_at,window,plan_snapshot,metrics,orders,spend_entries。买家/订单为独立虚构记录，不能写入现场 orders。
- 批次以明确配置版本保存，消耗固定场景或预算相应比例必须预览展示，不暗示预测。重复请求幂等。不同批次可独立选择，绝不随刷新随机。

## 待办

- POST /tasks/scan `{campaign_id,batch_id?,spend_threshold:100,request_id}` -> 该活动 Task[]。无批次扫描待确认素材/计划；有批次扫描无成交、预算接近上限；使用稳定对象/规则/窗口键去重，不覆盖已处理状态。
- Task: id,campaign_id,title,detail,rule,object_type,object_id,plan_id?,batch_id?,evidence,status(pending/processing/review/resolved/ignored),note,created_at,history[]。
- POST /tasks/{id}/status `{status,note}` -> Task，解决/忽略需理由。

## 复盘和观察

- POST /insights 支持 dataset=batch,batch_id,plan_id,date_from/date_to,request_id，保存 analytics_snapshot 与明确范围。
- 现有 /insights/{id}/accept 保持返回 Creative，同时自动创建待确认 Observation；同一条建议只接受一次目标动作（素材/计划二选一）。
- POST /insights/{id}/dismiss `{reason}` -> Insight，pending 可暂不采纳，已采纳不可改为拒绝。
- 计划动作使用上述 adjustments 的 insight_id；不做无人确认执行。
- Observation: id,campaign_id,insight_id?,adjustment_id?,creative_id?,plan_id?,baseline_dataset,baseline_batch_id?,baseline_snapshot,status(waiting_confirmation/observing/reviewed),metric:'支付订单',start_at,end_at?,note,comparison?。
- POST /observations/{id}/start `{plan_id}` 绑定已确认素材的运行计划（或调整对应的计划），保存起点，状态 observing。
- POST /observations/{id}/review `{batch_id?,note}` -> Observation；无匹配数据返回保持 observing 并具体解释缺失；只有与计划/版本相符、独立且在观察开始后载入的同源模拟批次才能进行批次前后比较。不把历史D0与现场混比。session 只比较可比订单/点击窗口，消耗/ROI仍空；不改变已有状态为自动成功。

## 报告

- POST /reports `{campaign_id,dataset,batch_id?,plan_id?,date_from?,date_to?,title,conclusion,next_action,request_id}` -> Report。
- Report: id,campaign_id,title,created_at,conclusion,next_action,simulation:true,snapshot:{campaign,analytics,creatives,plans,tasks,adjustments,observations,model_label}。
- 保存时深拷贝快照，旧报告不可更新；改结论生成新报告。前端可预览、打印，事实和人工结论分区。

## 前端分工接口

App.tsx/api.ts/Poster.tsx/main-v2.css 由 core-ui 负责。Feedback.tsx/feedback.css 由 feedback-ui 负责，不互相覆盖文件。

`FeedbackPages` 默认导出 props: `{page:'tasks'|'optimize'|'reports',state:State,campaignId:string,dataset:string,batchId:string,planId:string,dateFrom:string,dateTo:string,busy:boolean,act:(fn:()=>Promise<unknown>,success?:string)=>Promise<void>,go:(page:string)=>void,setDataset:(s:string)=>void,setBatchId:(s:string)=>void,setPlanId:(s:string)=>void}`。组件使用自身弹窗和内部受控表单。act 出错必须由根显示且不可误关表单。数据范围筛选由 App 统一展示。

State 新记录数组 types 由 core-ui 写，反馈组件可自行 export 本地类型或使用 Record<string,any> 临时兼容，整合时收紧。后端 agent 若改变契约必须立即通知其他人。
